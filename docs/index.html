ReservaYa

Reservas de buses intermunicipales. Una API que no se cae cuando dos personas pelean por el mismo asiento.

stack: FastAPI · MySQL · Redis · RabbitMQ infra: Docker Compose repo →

qué resuelve

Un pasajero entra, mira las rutas disponibles, elige asiento para una fecha concreta y paga. Recibe la factura en su correo. Punto.

Lo interesante no es el CRUD. Es que la disponibilidad de cada asiento depende del día del viaje —el asiento A1 del bus Bogotá→Medellín puede estar libre el martes y ocupado el viernes— y que dos personas reservando el mismo asiento al mismo tiempo nunca terminen ambas con el cupo.

Hay un panel de administrador aparte: crear rutas, fijar precio y capacidad, ver todas las reservas, y revisar si MySQL / Redis / RabbitMQ están vivos.

cómo está armado

Siete contenedores hablando por la red interna de Docker. La API nunca toca SMTP ni bloquea esperando que salga un correo: publica un evento y sigue.

  navegador
      │  HTTP
      ▼
 ┌─────────────┐     FOR UPDATE + índice único
 │  app        │────────────────► MySQL   reservas, rutas, users
 │  (FastAPI)  │
 │             │────► Redis   sesiones por token + caché
 │             │
 │             │──┐   publica evento "reserva_creada"
 └─────────────┘  ▼
              RabbitMQ  (cola durable)
                  │  consume
                  ▼
          ┌──────────────┐
          │  worker      │──► SMTP → factura al correo
          │  (consumer)  │──► Redis → registro de actividad
          └──────────────┘

El worker es un proceso aparte. Si el correo falla, la reserva ya está guardada y confirmada —el fallo del email no revienta la transacción.

el problema del asiento

Dos clientes, mismo asiento, misma fecha, mismo milisegundo. Sin protección, ambos leen "libre" y ambos insertan. Doble venta.

La defensa son dos capas, no una:

  • Lock de fila — SELECT ... FROM rutas WHERE id=? FOR UPDATE. Serializa todas las reservas de esa ruta: entran en fila, una termina antes de que empiece la siguiente.
  • Índice único — (ruta_id, asiento, fecha_reserva). La última palabra la tiene la base de datos. Aunque el lock fallara, el segundo INSERT rebota.

Probado con 30+ requests concurrentes al mismo asiento: exactamente uno gana (201), el resto recibe 409. Cero filas duplicadas en GROUP BY ... HAVING COUNT(*) > 1. El script de prueba está en concurrency_test.py.

decisiones y por qué

¿por qué una cola para los correos?

Mandar un email tarda segundos y puede fallar. No quiero que el usuario espere —ni que un timeout de Gmail tumbe la reserva. RabbitMQ desacopla: la API confirma rápido, el worker manda el correo cuando puede.

¿por qué la fecha en el índice único?

Un bus repite ruta cada día. El asiento no es único por ruta, es único por ruta+día. Meter fecha_reserva en el índice fue lo que hizo posible reservar el mismo asiento en fechas distintas sin trampas.

¿por qué sesiones en Redis y no JWT?

Quería poder invalidar una sesión al instante (logout real, expiración server-side). Con un token opaco guardado en Redis, borrar la clave mata la sesión. Con JWT tendría que esperar a que expire.

¿por qué migraciones en el arranque y no Alembic?

El esquema base llega por init.sql. Las columnas nuevas (precio, email, estado_pago) se agregan con SHOW COLUMNS ... IF NOT EXISTS al levantar la app. Para el tamaño del proyecto, una herramienta de migraciones sobraba.

correrlo

Solo necesitas git y docker. En Windows, todo dentro de WSL.

git clone https://github.com/nicolasgarciae/proyecto1corte.git
cd proyecto1corte

make setup          # crea .env
nano .env           # pon tus contraseñas

make up             # construye y levanta los 7 servicios

Comprobar que respondió:

curl http://localhost:8014/health
# {"status": "ok"}

App en localhost:8014. Admin: admin / admin.

Los correos son opcionales: si dejas SMTP_HOST vacío en el .env, todo funciona menos el envío. Para activarlos, una cuenta Gmail con contraseña de aplicación. La guía larga está en el README.
